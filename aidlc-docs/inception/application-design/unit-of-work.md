# Unit of Work — 유닛 정의서 (테이블오더 서비스)

## 개요
테이블오더 서비스를 5명의 개발자가 병렬로 개발할 수 있도록 **5개의 유닛(Unit of Work)** 으로 분할한다. 각 유닛은 담당 기능의 **백엔드 API + 프론트엔드 UI를 모두 포함하는 풀스택 유닛**이다(확정 질문 Q4=A).

**기술 스택 (확정)**: Python 백엔드 · Vue 프론트엔드 · SQLite · 로컬 실행 · 모노레포 · SSE
**규모**: 소규모(단일 매장, 수십 개 테이블)
**활성 확장**: PBT Partial(강제: PBT-02, PBT-03, PBT-07, PBT-08, PBT-09) / Security·Resiliency 비활성

## 분할 원칙
1. **도메인 응집도**: 관련 기능을 하나의 유닛으로 묶음
2. **의존성 최소화**: 공유 기반(스키마/모델/API 계약)을 Unit 1에서 조기 확정하여 병렬성 확보 (Q3=A)
3. **균등한 작업량**: 5명에게 유사한 규모 배분
4. **명확한 소유권**: 유닛당 주 담당 개발자 1명

---

## 유닛 정의

### Unit 1: Foundation & Shared Core (공통 기반)
- **담당**: 김주영 (초기 리드)
- **책임**:
  - 모노레포 프로젝트 스캐폴딩(백엔드/프론트 디렉토리 구조)
  - SQLite 스키마 및 마이그레이션
  - 공유 데이터 모델: Store, Table, TableSession, Menu, Category, Order, OrderItem, OrderHistory, AdminUser
  - 공통 유틸: DB 접근 계층, 표준 에러 응답 포맷, 검증 헬퍼
  - **API 계약(OpenAPI/스키마) 초안** — 전 유닛 공유
  - SSE 인프라 공통 모듈(이벤트 브로커/발행·구독 유틸)
- **경계(In)**: 저장소 스키마, 도메인 모델, 공통 계약, SSE 기반 모듈
- **경계(Out)**: 개별 화면·비즈니스 플로우(각 기능 유닛 소유)
- **비고**: 다른 모든 유닛이 의존. **계약을 가장 먼저 짧게 확정**한 뒤 병렬 개발 시작(Q3=A)

### Unit 2: Customer Ordering (고객 주문 · 풀스택)
- **담당**: 박찬준
- **책임**:
  - 테이블 태블릿 자동 로그인/세션 소비(저장된 정보 기반)
  - 메뉴 조회·탐색(카드 UI, 카테고리 이동, 상세 정보)
  - 장바구니 관리(추가/삭제, 수량 조절, 총액 실시간 계산, 로컬 저장·새로고침 유지)
  - 주문 생성(최종 확인, 확정, 주문번호 표시, 장바구니 비우기, 메뉴 화면 자동 리다이렉트, 실패 시 유지)
  - 현재 세션 주문 내역 조회(시간순, 상태 표시, 현재 세션만 필터)
- **포함 요구사항**: 3.1.1 ~ 3.1.5
- **경계**: 고객용 웹UI + 고객 대상 백엔드 API. 세션/메뉴/주문 데이터는 Unit 1 모델·계약 사용

### Unit 3: Admin Auth & Real-time Monitoring (관리자 인증 + 실시간 모니터링 · 풀스택)
- **담당**: 임동규
- **책임**:
  - 매장 인증: JWT 발급, 16시간 세션, bcrypt 해싱, 로그인 시도 제한, 새로고침 시 세션 유지
  - 실시간 주문 모니터링: SSE 소비, 그리드/대시보드 레이아웃, 테이블별 카드(총 주문액·최신 주문 미리보기), 주문 상세 보기, 상태 변경(대기중/준비중/완료), 신규 주문 시각 강조, 테이블 필터링
- **포함 요구사항**: 3.2.1, 3.2.2
- **경계**: 관리자 인증·모니터링 UI + 관련 API. Unit 2/4가 발행한 SSE 이벤트 소비

### Unit 4: Table & Session Management (테이블·세션 관리 · 풀스택)
- **담당**: 이명우
- **책임**:
  - 테이블 태블릿 초기 설정(번호/비밀번호, 16시간 세션 생성, 자동 로그인 활성화)
  - 주문 삭제(직권 수정: 확인 팝업, 즉시 삭제, 총액 재계산, 피드백)
  - 테이블 세션 라이프사이클(첫 주문으로 세션 시작, 이용 완료로 종료, 이력 이동, 총액 0 리셋)
  - 과거 주문 내역 조회(테이블별 시간 역순, 날짜 필터, 완료 시각 표시)
- **포함 요구사항**: 3.2.3
- **경계**: 테이블 관리 UI + 관련 API. Session/Order/OrderHistory 모델은 Unit 1 사용, 상태 변경은 SSE 이벤트 발행

### Unit 5: Menu Management (메뉴 관리 · 풀스택)
- **담당**: 윤태경
- **책임**:
  - 메뉴 CRUD(등록/수정/삭제/조회)
  - 카테고리별 관리, 노출 순서 조정
  - 데이터 검증(필수 필드, 가격 범위)
  - 관련 관리자 UI
- **포함 요구사항**: 3.2.4
- **경계**: 메뉴 관리 UI + 관련 API. Menu/Category 모델은 Unit 1 사용, Unit 2(고객 메뉴 조회)가 데이터 소비

## 개발자 배정
| 유닛 | 개발자 | 성격 |
|---|---|---|
| Unit 1: Foundation & Shared Core | 김주영 | 기반 — 계약 조기 확정, 초기 리드 |
| Unit 2: Customer Ordering | 박찬준 | 풀스택(고객) |
| Unit 3: Admin Auth & Monitoring | 임동규 | 풀스택(인증 + SSE) |
| Unit 4: Table & Session Mgmt | 이명우 | 풀스택(세션 라이프사이클) |
| Unit 5: Menu Management | 윤태경 | 풀스택(CRUD) |

## 코드 구성 전략 (Greenfield · 모노레포)
확정 질문 Q5=A(모노레포, 백엔드/프론트 분리 디렉토리) 기준.

```text
table-order/                     # 워크스페이스 루트 (애플리케이션 코드)
├── backend/                     # Python 백엔드
│   ├── app/
│   │   ├── core/                # Unit 1: DB, 모델, 공통 유틸, SSE 브로커
│   │   ├── customer/            # Unit 2: 고객 주문 API
│   │   ├── admin_auth/          # Unit 3: 인증 + 모니터링(SSE 엔드포인트) API
│   │   ├── tables/              # Unit 4: 테이블·세션 관리 API
│   │   └── menu/                # Unit 5: 메뉴 관리 API
│   ├── migrations/              # Unit 1: SQLite 스키마/마이그레이션
│   └── tests/                   # 유닛별 테스트 (PBT 포함)
├── frontend/
│   ├── customer/                # Unit 2: 고객용 Vue 앱
│   └── admin/                   # Unit 3/4/5: 관리자용 Vue 앱(모니터링/테이블/메뉴 화면)
├── shared/                      # Unit 1: API 계약(OpenAPI/스키마), 공유 타입
└── aidlc-docs/                  # 문서 (코드 아님)
```

**병렬 개발 규칙**:
- Unit 1이 `shared/`의 API 계약과 `backend/app/core/` 모델·스키마를 **먼저 확정**한 뒤 나머지 4개 유닛이 동시 진행(Q3=A).
- 관리자용 프론트(Unit 3/4/5)는 동일한 `frontend/admin/` Vue 앱 내 별도 라우트/모듈로 분리하여 충돌 최소화.

## 검증 요약
- **경계 명확성**: 각 유닛은 요구사항 기능군과 1:1 대응, 책임 중복 없음.
- **공유 자원**: DB 스키마·도메인 모델·SSE 기반·API 계약은 Unit 1에 단일 소유로 집중.
- **요구사항 커버리지**: 3.1.1~3.1.5, 3.2.1~3.2.4 전부 유닛에 배정됨(누락 없음, story-map 참조).
- **작업 균형**: Q5=A로 현재 분할 유지(규모 차이 수용).
