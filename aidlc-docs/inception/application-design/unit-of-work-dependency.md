|---|---|---|---|---|---|
| **U1 Foundation** | — | — | — | — | — |

| **U4 Table/Session** | ✔ | — | — | — | — |

## 의존성 상세

### 강한 의존 (Hard — 계약/모델 공유)
- **U2, U3, U4, U5 → U1**: 모든 기능 유닛이 Unit 1의 공유 데이터 모델·SQLite 스키마·API 계약·SSE 기반 모듈에 의존.
  - **해소 전략**: Unit 1이 API 계약과 도메인 모델을 **가장 먼저 짧게 확정**(Q3=A). 확정된 계약을 인터페이스로 삼아 나머지 유닛이 병렬 개발.

### 이벤트 의존 (Runtime — SSE 발행/구독)
- **U3 → U2**: U2의 주문 생성이 발행하는 SSE 이벤트를 U3 모니터링이 소비.
- **U3 → U4**: U4의 주문 삭제·세션 종료·상태 변경이 발행하는 SSE 이벤트를 U3 모니터링이 소비.
  - **해소 전략**: SSE 이벤트 스키마(이벤트 타입·페이로드)를 Unit 1의 공통 계약에 정의. 발행측(U2/U4)과 구독측(U3)이 동일 계약 준수.

### 데이터 의존 (Data)
- **U2 → U5**: U2 고객 메뉴 조회가 U5가 관리하는 메뉴/카테고리 데이터를 읽음.
  - **해소 전략**: Menu/Category 모델·조회 API를 Unit 1 계약에 정의. U5는 쓰기, U2는 읽기.
- **U2 ↔ U4 (세션 개념 공유)**: U4가 관리하는 테이블 세션 라이프사이클을 U2의 "현재 세션 주문만 조회" 필터가 참조.
  - **해소 전략**: TableSession 모델과 "현재 세션" 판별 규칙을 Unit 1 계약에 정의.

## 개발 순서 (병렬 전략, Q3=A)

```text
[Phase 0] Unit 1 — API 계약 + 도메인 모델 + 스키마 짧게 확정  (김주영, 초기 리드)
                    │
                    ▼  (계약 확정 후 인터페이스 고정)
[Phase 1] ┌─ Unit 2 (박찬준) ─┐
          ├─ Unit 3 (임동규) ─┤   ← 4개 유닛 동시 병렬 개발
          ├─ Unit 4 (이명우) ─┤
          └─ Unit 5 (윤태경) ─┘
                    │
                    ▼
[통합]    SSE 이벤트 · 메뉴 데이터 · 세션 필터 계약 기준 통합/검증
```

## 순환 의존성 점검
- 매트릭스상 순환 의존 **없음**. U1은 어떤 유닛에도 의존하지 않는 최하위 기반 유닛.
- U2↔U4는 "세션 개념 공유"이나 실제 코드 의존은 U1 모델을 통해 간접적으로 이루어져 순환이 아님.

## 계약 우선 항목 (Unit 1이 Phase 0에서 확정해야 할 것)
1. 도메인 모델 스키마: Store, Table, TableSession, Menu, Category, Order, OrderItem, OrderHistory, AdminUser
2. REST API 계약: 고객 주문, 인증, 모니터링, 테이블/세션, 메뉴 엔드포인트 시그니처
3. SSE 이벤트 계약: 이벤트 타입(주문 생성/상태 변경/삭제/세션 종료)과 페이로드 구조
4. "현재 세션" 판별 규칙 및 총액 계산 규칙
5. 표준 에러 응답 포맷
